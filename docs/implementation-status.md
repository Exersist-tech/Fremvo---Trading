# Implementation Status

## Paper-training evidence

- Approved strategy templates retain individual approval and parameter
  provenance while their Kraken Spot symbols are selected dynamically.
- The continuous scanner pins a compiled, approved version per strategy family
  on admission (v3/v4/v5 for new plans); existing workers retain their
  original version and saved parameters. Exact regime/signal/execution roles
  use 320 chronological closed candles per requested role.
- The authenticated `/experiments` Start flow enables a continuous scanner with
  no preallocated workers. Every five minutes it discovers Kraken's active,
  sufficiently liquid EUR Spot pairs, loads each family's approved closed
  regime/signal/execution evidence, and evaluates only profiles whose signal
  candle has newly closed. HOLD, vetoed, rejected, and queued observations
  consume no worker. At most ten ranked opportunities are admitted; each
  receives an isolated fake-EUR worker and pair diversity is preferred before
  reuse. Exact selected slots, scan observations, and Stop state survive
  restarts. The market-data host derives subscriptions from the active profiles,
  including 1m, 4h, and 1d where required, and backfills 320 authoritative
  closed bars. Each role is cut off at its own most recent completed UTC
  boundary, preventing future or forming candles from entering a decision.
  Decision identity remains bound to the closed signal candle rather than the
  host tick, preventing repeated orders from one candle. Complete
  neutral outcomes are retained in the decision ledger for
  diagnosis, while temporarily unavailable startup evidence remains a no-op so
  backfill cannot freeze an incomplete decision. Missing or blocked evidence
  fails closed. Later supporting candles cannot rewrite an already neutral
  decision for the same primary candle; the first complete decision is
  preserved without faulting the worker. After a completed fill changes the
  worker portfolio, re-evaluating that same primary candle returns its already
  accepted decision unchanged instead of attempting to reinterpret `Open` as
  `Neutral` or `Add`; changed evidence under the same identity still conflicts
  and fails closed. Decision fingerprints commit to all three role series.
  Paper sizing applies quantity steps and minimum notionals while
  treating the closed-candle entry and ATR stop as market references rather
  than limit prices; low-priced assets are no longer blocked by an unrelated
  one-unit cap. Only the simulated paper adapter is registered; no venue order
  gateway is reachable.

| Task | Status | Notes |

| 9.1 ISpotOrderGateway Kraken Spot implementation | Done | 2026-09-20 — `ISpotOrderGateway` (exchange-neutral) and `KrakenSpotOrderGateway` cover place, cancel, query and fills against Kraken's real Spot API shape. Every order carries the platform's own id in Kraken's `cl_ord_id` field, so **Kraken itself enforces idempotency** — a reused id is refused by the exchange rather than deduplicated on hope — and an order stays findable after a timeout, when Kraken's own identifier is exactly what never arrived. Cancel and query are keyed on the same id for the same reason. **The central rule is that "refused" and "we do not know" are different answers and never merge.** A placement is `Rejected` only when Kraken complained about the order's own content, because only then is it certain no order was created; timeouts, network failures, rate limits, nonce errors, unreadable bodies and any error string this connector has never seen all return `Indeterminate`, which obliges the caller to reconcile rather than resubmit. That asymmetry is deliberate: an unnecessary reconciliation query costs one API call, while a wrong "not placed" costs a duplicate live position. A reused `cl_ord_id` is reported as `DuplicateClientOrderId` — evidence that an earlier submission *succeeded* — and a rejection cannot even be constructed without the exchange's reason, so it cannot be mistaken for silence. `ValidateOnly` **defaults to true**, so a caller that forgets to state its intent asks Kraken to check an order rather than place one, and a validated request returns `Validated`, never `Accepted`, so a dry run can never be read as exposure. A cancellation Kraken answers with a count of zero is `NotFound`, not `Cancelled`. An unrecognised order status is `Unavailable` rather than guessed. An unanswered fill query returns `Unavailable` with an empty list that must not be read as "no fills". All money and quantity fields are parsed straight into `decimal` with the invariant culture, never through a binary floating-point type; timestamps are UTC; a fill reports **no fee currency** because Kraken does not state one and an assumed quote asset would silently misstate cost, so the pair is carried for the instrument catalogue to resolve. There is no withdrawal, transfer or funding member, and a test asserts none exists. **This does not enable live trading:** the gateway is not registered in DI and does not implement `ILiveExecutionRoute`, and a test asserts it stays that way until 9.2–9.6 land. |

Two properties make it safe rather than merely convenient: an **unscripted path throws** instead of falling through, so a test can never reach the real api.kraken.com, and a **script that runs out of steps throws** instead of repeating its last answer, so a retry loop cannot be validated against evidence nobody recorded. | 9.4 Reconciliation wiring + error taxonomy | Done | 2026-09-21 — `SpotOrderStatusQuery` binds the neutral gateway to `IExchangeOrderStatusQuery`, closing the loop opened in 8.7: the adapter can report that nothing was established, and this is what establishes it.
