## Platform changes

| Change | Date | Notes |
|---|---|---|
| Build output removed from version control | 2026-09-20 | The repository had no `.gitignore` and was tracking 904 `bin/` and `obj/` files. This was not merely untidy: because the compiled assemblies were versioned, ordinary git operations rewrote them on disk, and the host's Application Control policy then refused to load `Trading.Infrastructure.Data.dll`, failing four persistence tests for reasons that had nothing to do with the code. Untracking the build output fixed those failures. A `.gitignore` now covers build, test and IDE output, and additionally ignores credential-shaped files so a developer secrets file or certificate cannot become a commit. |
| Trading stage moved onto the exchange account | 2026-09-20 | Simulated and real money are now a property of the account (`TradingStage`: `Paper`, `Proving`, `Live`) rather than anything the user interface can switch. A view toggle between fake and real money would imply one account can move between them freely, which is how accidental real orders happen. Every account starts in `Paper`; `Paper` is deliberately the default enum value `0`, so a row written without an explicit stage falls back to the one that cannot reach the exchange. Stages advance one step at a time and cannot be skipped, so nothing can jump from simulated straight to live and bypass the proving stage. An account that is not connected and validated cannot be promoted at all, so a stale or broken connection can never be cleared to trade. `CanReachExchange` is false for every `Paper` account no matter how healthy its connection is. Disconnecting or suspending resets the stage to `Paper`, so re-connecting a key never silently restores a previously granted live clearance, and returning to `Paper` is always permitted because a safety action must never be blocked by the state it is correcting. Promotion beyond `Paper` remains unreachable from the product until Phases 8 to 10 are complete. |
| Local development sign-in bootstrap | 2026-09-20 | Added `DevelopmentDataSeeder` so the application can be explored as a signed-in user on a developer machine. Two blockers were fixed honestly rather than bypassed. **First, the authentication cookie is `CookieSecurePolicy.Always`,** so it is never sent over plain HTTP and no signed-in page could work on `http://localhost`. This was solved by running over HTTPS with the ASP.NET Core development certificate, **not** by weakening the cookie policy and **not** by adding an authentication-bypass switch — a bypass flag in a trading platform is exactly the kind of setting that escapes into production. **Second, no schema existed,** because no migrations exist yet; the seeder calls `EnsureCreatedAsync`, which is a local bootstrap only and is explicitly **not** a substitute for the migration work each phase still owes. The seeder is guarded twice: it is a no-op unless `Development:SeedDemoData` is set, and it throws on startup if that flag is ever set outside the Development environment, so demo accounts cannot be created in a real environment. It seeds an administrator (`admin@fremvo.local`), a standard user (`trader@fremvo.local`), and one invitation code. The administrator is created with multi-factor authentication already enabled because the domain refuses administrator privilege without it — seeding it disabled would have produced an account that looks privileged but fails on use. No trading capability is granted: live trading stays off and the demo users hold no exchange credentials. Verified at runtime that authorization was not weakened: anonymous calls to `/api/orders` and `/api/risk/halts` return 401, and the standard user receives 403 on `POST /api/risk/halts` and `GET /api/universe/instruments` while the administrator receives 200. **Known gap reconfirmed during this work:** `AuthenticationService` still performs no password verification — any password of eight or more characters signs in an active user. This is tracked for the credential-hardening task and must be closed before any non-local deployment. **Follow-up on 2026-09-20:** `EnsureCreated` decides at the database level rather than the table level, so a `Crypto` database left over from earlier work kept its old three-table schema and silently lacked every table added since, surfacing only as `Invalid object name 'ExchangeAccounts'` at request time. The seeder now compares the model's tables against `sys.tables` and rebuilds the development database when any are missing, logging a warning. This is a direct consequence of having no migrations and is not a pattern any deployed environment may use. Build clean; 335 tests passing. |
| Exchange switched from Binance to Kraken | 2026-09-20 | The first supported venue is now Kraken, for access reasons. `Trading.Exchanges.Binance` was renamed to `Trading.Exchanges.Kraken` and its wire mapping rewritten against Kraken's real `AssetPairs` response, verified live against `api.kraken.com`. Two substantive findings came out of the switch rather than a rename alone. **First, a domain vocabulary leak:** `Instrument` hard-coded Binance's literal strings `"TRADING"` and `"SPOT"`, so against Kraken — whose statuses are `online`, `cancel_only`, `post_only`, `limit_only`, `reduce_only`, `maintenance` — every instrument would have been silently ineligible forever. Replaced with the neutral `InstrumentTradingStatus` enum and `InstrumentCapabilities` constants, mirrored as `CatalogueTradingStatus` in the exchange abstraction and mapped in `CatalogueSynchronizer`, so no venue's vocabulary reaches the domain. An unrecognised status maps to `Unknown`, which is never tradable, so a status Kraken adds later cannot be read as permission to trade. **Second, Kraken publishes no public Spot sandbox** (only Futures has one, at `demo-futures.kraken.com`), which invalidated the plan's "Spot testnet before live" safety gate. The gate was redesigned rather than dropped: Phase 9 is now a recorded-response replay harness for CI plus a supervised minimum-size proving stage whose notional ceiling is enforced in the risk engine, and an explicit test asserts no automated test can place a real order. Kraken also supplies no listing date, so listing age is now genuinely unknown and fails the new-listing gate. The 50-pair seed moved to Kraken USD pairs using Kraken's own codes (`XBT`, `XDG`) under version tag `2026-09-20.kraken-spot-usd-50`. Build clean; 335 tests passing. |

## Phase 9 — Kraken Spot proving stage (replay harness + minimum-size live path)
| Task | Status | Notes |
|---|---|---|
| 9.1 ISpotOrderGateway Kraken Spot implementation | Done | 2026-09-20 — `ISpotOrderGateway` (exchange-neutral) and `KrakenSpotOrderGateway` cover place, cancel, query and fills against Kraken's real Spot API shape. Every order carries the platform's own id in Kraken's `cl_ord_id` field, so **Kraken itself enforces idempotency** — a reused id is refused by the exchange rather than deduplicated on hope — and an order stays findable after a timeout, when Kraken's own identifier is exactly what never arrived. Cancel and query are keyed on the same id for the same reason. **The central rule is that "refused" and "we do not know" are different answers and never merge.** A placement is `Rejected` only when Kraken complained about the order's own content, because only then is it certain no order was created; timeouts, network failures, rate limits, nonce errors, unreadable bodies and any error string this connector has never seen all return `Indeterminate`, which obliges the caller to reconcile rather than resubmit. That asymmetry is deliberate: an unnecessary reconciliation query costs one API call, while a wrong "not placed" costs a duplicate live position. A reused `cl_ord_id` is reported as `DuplicateClientOrderId` — evidence that an earlier submission *succeeded* — and a rejection cannot even be constructed without the exchange's reason, so it cannot be mistaken for silence. `ValidateOnly` **defaults to true**, so a caller that forgets to state its intent asks Kraken to check an order rather than place one, and a validated request returns `Validated`, never `Accepted`, so a dry run can never be read as exposure. A cancellation Kraken answers with a count of zero is `NotFound`, not `Cancelled`. An unrecognised order status is `Unavailable` rather than guessed. An unanswered fill query returns `Unavailable` with an empty list that must not be read as "no fills". All money and quantity fields are parsed straight into `decimal` with the invariant culture, never through a binary floating-point type; timestamps are UTC; a fill reports **no fee currency** because Kraken does not state one and an assumed quote asset would silently misstate cost, so the pair is carried for the instrument catalogue to resolve. There is no withdrawal, transfer or funding member, and a test asserts none exists. **This does not enable live trading:** the gateway is not registered in DI and does not implement `ILiveExecutionRoute`, and a test asserts it stays that way until 9.2–9.6 land. |
| 9.2 KrakenSpotExecutionAdapter | Done | 2026-09-21 — `SpotExecutionAdapter` turns a pipeline `ExecutionCommand` into a real spot order. **It is written against `ISpotOrderGateway` and names no exchange type**, so it was placed in `Trading.Application` rather than the Kraken connector as the plan originally proposed; Kraken's encoding, error strings and response shapes stay behind the gateway, and a second exchange becomes a new gateway rather than an edit here. It is the last checkpoint before real money and each of its four conditions **refuses rather than adapts**: a paper-only command is never sent to a venue, a command with no resolvable account is refused, an account still in `Paper` stage is refused, and an account belonging to another exchange is refused. None of these falls back to simulation, because quietly simulating a real order would report a fill the user does not hold. Two domain changes support it. `ExecutionResult` now carries an `ExecutionOutcome` of `Filled`, `Rejected` or **`Unknown`**, so the adapter can say "nothing was established" instead of collapsing a timeout into a refusal — `RequiresReconciliation` is the flag callers act on; an omitted outcome derives `Success ? Filled : Rejected`, which is safe only for callers such as the paper adapter that cannot be in doubt. And `ExecutionCommand` now carries an `ExchangeAccountId` that **a non-paper command cannot be constructed without**, so the adapter never has to infer whose money is at risk. Acceptance is deliberately not reported as a fill: quantity, price and fees stay zero until fills are read back, so an accepted limit order cannot invent a position at its limit price. A duplicate `cl_ord_id` and a validate-only answer to a real order both degrade to `Unknown`, never to `Rejected`. Credentials are resolved per execution through `ISpotExecutionAccountSource` and never held, logged or returned; a test asserts the secret never reaches a failure message. |
| 9.3 Recorded-response replay harness + Kraken fixtures | Done | 2026-09-21 — `KrakenReplayHandler` replays recorded Kraken answers to the unmodified production connector. Kraken publishes no public Spot sandbox, so "rehearse the route before real money" cannot mean a venue test environment; this is the substitute, and it is what makes the first real order a repeat of something already seen. **It lives in the test assembly on purpose** — a component that can fabricate an exchange answer must not be shippable inside the connector, which is why the plan's nomination of `Trading.Exchanges.Kraken` was not followed. Two properties make it safe rather than merely convenient: an **unscripted path throws** instead of falling through, so a test can never reach the real api.kraken.com, and a **script that runs out of steps throws** instead of repeating its last answer, so a retry loop cannot be validated against evidence nobody recorded. Every request is captured with its form fields parsed out, so a test asserts what was actually sent rather than what was intended. Fixtures cover acceptance, validate-only, content rejections, rate limits, empty bodies, open orders, partial fills, closed orders and the empty result set that is Kraken's only proof an order is absent. Timeouts and transport failures are first-class scripted steps, because the unanswered request is the case the whole reconciliation path exists for. |
| 9.4 Reconciliation wiring + error taxonomy | Done | 2026-09-21 — `SpotOrderStatusQuery` binds the neutral gateway to `IExchangeOrderStatusQuery`, closing the loop opened in 8.7: the adapter can report that nothing was established, and this is what establishes it. The credential is resolved **per call** rather than captured at construction, so a revoked or rotated key takes effect immediately and no long-lived object holds a secret. **Every failure path returns `Unavailable` and none returns `NotFound`**, because only the exchange can prove an order's absence and a local failure proves nothing — an unresolvable account, a wrong-exchange binding and an unanticipated connector exception all degrade the same way. The Kraken error taxonomy gained the venue's precision and filter refusals (tick size, limit price, unknown asset, order and position limits) as definite refusals, and an **explicit inconclusive list** — rate limits, nonce errors, temporary lockouts, service busy and internal errors — checked *before* the refusal list so a message carrying both cannot be mistaken for proof of absence. Naming those explicitly is the point: a future edit that reclassifies a rate limit as a refusal now has to delete a written statement that it is not one. End-to-end tests over the replay harness prove the four outcomes of an unanswered order: Kraken never received it → safe to resubmit; Kraken holds it open → adopted, never resubmitted; Kraken already filled it → the fill is adopted; Kraken cannot be reached → the order stays frozen and a human is needed. A further test asserts reconciliation queries by **client order id**, the identifier that survives a timeout, and that it sends no order of its own. |
| 9.5 ExchangeAccountTradingStage + proving ceiling enforcement | Done | 2026-09-21 — `ExchangeAccount` gained a nullable `ProvingNotionalCeiling` (decimal(18,8), never float) recording the largest single-order notional permitted while the account proves its live route. Because Kraken has no public sandbox, proving means real orders, and the ceiling is what keeps the cost of that proof small and known in advance. **It is enforced by the risk engine, not the execution adapter.** The adapter is the only component that can reach the exchange; a limit enforced only there would have nothing standing behind a bug in it. `ProvingRestriction` states the bounds in exchange-neutral terms — symbol, order notional, ceiling, approved instruments — so `Trading.Risk` keeps no dependency on the connector layer, and is evaluated alongside the mandatory platform ceilings where a user's own configuration cannot widen it. **A missing ceiling blocks every proving order rather than permitting any size**, and an empty approved-instrument set blocks everything, because "not configured" must read as "nothing approved". Only the platform can set the ceiling; a user has no path to raise it. Halts and stale data still report before a proving violation, so a platform-wide control is never masked by an account-level one. |
| 9.6 End-to-end replay integration suite + no-real-order guard test | Done | 2026-09-21 — 37 tests run the real connector, real adapter and real reconciliation service together over recorded answers: placement, validate-only encoding, content rejection, rate limit, timeout, empty server error, open/partial/closed order states, and the full unanswered-order path in all four of its resolutions. A test asserts the adapter **makes exactly one attempt** at an unanswered order and never retries on its own, which is the duplicate-position bug stated as an assertion. The guard against real orders rests on two independent facts, either of which alone would be enough: every request is answered by the replay handler, which throws on any unscripted path, and **every client in the suite targets the reserved `.invalid` top-level domain**, which by RFC 2606 can never resolve — so even a handler bypassed by a bug would fail to connect rather than reach Kraken. **Live trading is still not reachable.** The gateway remains unregistered in DI and still does not implement `ILiveExecutionRoute`; the canary test now records that the remaining gate is Phase 10's gated rollout, supervision and audit surface, so opening live trading has to be a decision rather than a side effect of this work. |
