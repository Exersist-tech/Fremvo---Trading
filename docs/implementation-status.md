## Platform changes

| Change | Date | Notes |
|---|---|---|
| Build output removed from version control | 2026-09-20 | The repository had no `.gitignore` and was tracking 904 `bin/` and `obj/` files. This was not merely untidy: because the compiled assemblies were versioned, ordinary git operations rewrote them on disk, and the host's Application Control policy then refused to load `Trading.Infrastructure.Data.dll`, failing four persistence tests for reasons that had nothing to do with the code. Untracking the build output fixed those failures. A `.gitignore` now covers build, test and IDE output, and additionally ignores credential-shaped files so a developer secrets file or certificate cannot become a commit. |
| Trading stage moved onto the exchange account | 2026-09-20 | Simulated and real money are now a property of the account (`TradingStage`: `Paper`, `Proving`, `Live`) rather than anything the user interface can switch. A view toggle between fake and real money would imply one account can move between them freely, which is how accidental real orders happen. Every account starts in `Paper`; `Paper` is deliberately the default enum value `0`, so a row written without an explicit stage falls back to the one that cannot reach the exchange. Stages advance one step at a time and cannot be skipped, so nothing can jump from simulated straight to live and bypass the proving stage. An account that is not connected and validated cannot be promoted at all, so a stale or broken connection can never be cleared to trade. `CanReachExchange` is false for every `Paper` account no matter how healthy its connection is. Disconnecting or suspending resets the stage to `Paper`, so re-connecting a key never silently restores a previously granted live clearance, and returning to `Paper` is always permitted because a safety action must never be blocked by the state it is correcting. Promotion beyond `Paper` remains unreachable from the product until Phases 8 to 10 are complete. |
| Local development sign-in bootstrap | 2026-09-20 | Added `DevelopmentDataSeeder` so the application can be explored as a signed-in user on a developer machine. Two blockers were fixed honestly rather than bypassed. **First, the authentication cookie is `CookieSecurePolicy.Always`,** so it is never sent over plain HTTP and no signed-in page could work on `http://localhost`. This was solved by running over HTTPS with the ASP.NET Core development certificate, **not** by weakening the cookie policy and **not** by adding an authentication-bypass switch — a bypass flag in a trading platform is exactly the kind of setting that escapes into production. **Second, no schema existed,** because no migrations exist yet; the seeder calls `EnsureCreatedAsync`, which is a local bootstrap only and is explicitly **not** a substitute for the migration work each phase still owes. The seeder is guarded twice: it is a no-op unless `Development:SeedDemoData` is set, and it throws on startup if that flag is ever set outside the Development environment, so demo accounts cannot be created in a real environment. It seeds an administrator (`admin@fremvo.local`), a standard user (`trader@fremvo.local`), and one invitation code. The administrator is created with multi-factor authentication already enabled because the domain refuses administrator privilege without it — seeding it disabled would have produced an account that looks privileged but fails on use. No trading capability is granted: live trading stays off and the demo users hold no exchange credentials. Verified at runtime that authorization was not weakened: anonymous calls to `/api/orders` and `/api/risk/halts` return 401, and the standard user receives 403 on `POST /api/risk/halts` and `GET /api/universe/instruments` while the administrator receives 200. **Known gap reconfirmed during this work:** `AuthenticationService` still performs no password verification — any password of eight or more characters signs in an active user. This is tracked for the credential-hardening task and must be closed before any non-local deployment. **Follow-up on 2026-09-20:** `EnsureCreated` decides at the database level rather than the table level, so a `Crypto` database left over from earlier work kept its old three-table schema and silently lacked every table added since, surfacing only as `Invalid object name 'ExchangeAccounts'` at request time. The seeder now compares the model's tables against `sys.tables` and rebuilds the development database when any are missing, logging a warning. This is a direct consequence of having no migrations and is not a pattern any deployed environment may use. Build clean; 335 tests passing. |
| Exchange switched from Binance to Kraken | 2026-09-20 | The first supported venue is now Kraken, for access reasons. `Trading.Exchanges.Binance` was renamed to `Trading.Exchanges.Kraken` and its wire mapping rewritten against Kraken's real `AssetPairs` response, verified live against `api.kraken.com`. Two substantive findings came out of the switch rather than a rename alone. **First, a domain vocabulary leak:** `Instrument` hard-coded Binance's literal strings `"TRADING"` and `"SPOT"`, so against Kraken — whose statuses are `online`, `cancel_only`, `post_only`, `limit_only`, `reduce_only`, `maintenance` — every instrument would have been silently ineligible forever. Replaced with the neutral `InstrumentTradingStatus` enum and `InstrumentCapabilities` constants, mirrored as `CatalogueTradingStatus` in the exchange abstraction and mapped in `CatalogueSynchronizer`, so no venue's vocabulary reaches the domain. An unrecognised status maps to `Unknown`, which is never tradable, so a status Kraken adds later cannot be read as permission to trade. **Second, Kraken publishes no public Spot sandbox** (only Futures has one, at `demo-futures.kraken.com`), which invalidated the plan's "Spot testnet before live" safety gate. The gate was redesigned rather than dropped: Phase 9 is now a recorded-response replay harness for CI plus a supervised minimum-size proving stage whose notional ceiling is enforced in the risk engine, and an explicit test asserts no automated test can place a real order. Kraken also supplies no listing date, so listing age is now genuinely unknown and fails the new-listing gate. The 50-pair seed moved to Kraken USD pairs using Kraken's own codes (`XBT`, `XDG`) under version tag `2026-09-20.kraken-spot-usd-50`. Build clean; 335 tests passing. |

| 7.8 Protective exits and the positions overview | Done | 2026-09-20 — closes the gap left open by 7.7. Fees, spread and slippage remain unmodelled, so an exit price here is an upper bound on the same exit placed live. |
